# Rust Core Migration Audit — 2026-05-16

## Scope

This audit identifies repository surfaces that are good candidates to convert
from shell, Python, JavaScript, or C glue into Rust and move behind Adze's core
design boundaries. It intentionally excludes fixture corpora, generated browser
assets, vendored Tree-sitter headers/sources, and sample language inputs unless
they currently behave as durable tooling.

The target design is:

- Rust-first implementation surfaces for durable behavior.
- `xtask` subcommands for repository automation.
- Published core crates or SRP owner modules for behavior that product code
  should consume.
- Thin `just` recipes and CI YAML that only dispatch to Rust-owned commands.
- Explicit non-Rust policy entries only for platform-required config, fixtures,
  generated artifacts, and genuinely external compatibility surfaces.

## Prioritized migration candidates

### P0 — Move release-surface and publish-order logic into `xtask`

**Current surface:** `scripts/release-surface.sh`,
`scripts/validate-release-surface.sh`, `scripts/publish-order.sh`,
`scripts/check-publish*.sh`, `scripts/dry-run-publish.sh`, and their `just`
wrappers.

**Why it should move:** These scripts decide the publishable package set,
validate metadata, compute topological publish order, and run release dry-runs.
That is repository policy, not shell glue. The logic overlaps with
`policy/package-boundary.toml` and Cargo metadata, so keeping it in shell makes
it hard to share with CI planning, docs, and release gates.

**Rust home:** Add `cargo xtask release-surface`,
`cargo xtask validate-release-surface`, and `cargo xtask publish-order` backed
by a shared release/package module that reads Cargo metadata plus
`policy/package-boundary.toml`.

**Core-design outcome:** Release decisions become a typed Rust policy API; CI,
`just`, and documentation can call the same implementation instead of
re-parsing Cargo metadata in multiple scripts.

**Suggested proof:**

```bash
cargo xtask publish-order --check
cargo xtask validate-release-surface
just publish-order
```

### P0 — Move CI plan emission from Python into `xtask`

**Current surface:** `scripts/ci/pr-plan.py`, `scripts/ci/emit-ci-actuals.py`,
and workflow steps that install Python only to emit CI planning metadata.

**Why it should move:** The workspace already has an `xtask ci-plan` command
and Rust policy modules for lane selection. Keeping CI summary/report emission
in Python creates a second implementation language for the same governance
surface.

**Rust home:** Extend `xtask::ci_plan` with summary rendering and actuals
emission, then retire the Python scripts after the workflows use the Rust
command.

**Core-design outcome:** PR lane selection, CI actuals, and policy reports are
all generated by one typed Rust implementation and can share parsing,
validation, and tests.

**Suggested proof:**

```bash
cargo xtask ci-plan --json-out target/ci/ci-plan.json
cargo xtask policy-report
```

### P1 — Move product-proof shell lanes into `xtask`

**Current surface:** `scripts/ci-product.sh`, `scripts/ci-product-stable.sh`,
`scripts/test-capped.sh`, `scripts/verify-cap-concurrency.sh`, and related
`just ci-product-*` recipes.

**Why it should move:** Product-proof lanes are part of the support-tier
contract. Shell is convenient for sequencing, but the lane definitions,
timeouts, concurrency caps, and advisory/stable classifications are structured
policy that should be validated and diffed in Rust.

**Rust home:** Add `cargo xtask product-proof --stable|--advisory --dry-run`
that loads a typed lane manifest and executes commands through a shared runner.
Keep the shell scripts as temporary compatibility wrappers until workflows and
`just` are migrated.

**Core-design outcome:** Support-tier proof commands become machine-readable,
testable, and reusable by docs/status generation.

**Suggested proof:**

```bash
cargo xtask product-proof --stable --dry-run
cargo xtask product-proof --advisory --dry-run
```

### P1 — Move clippy/debug/no-mangle orchestration into `xtask lint`

**Current surface:** `scripts/clippy-per-package.sh`,
`scripts/clippy-collect.sh`, `scripts/check-no-mangle.sh`, and portions of
`just clippy`/CI that call those scripts directly.

**Why it should move:** The repository already has `cargo xtask lint` plus Rust
policy modules for debug block validation and no-panic policy. Clippy package
selection, quarantine reporting, and symbol-export checks should be represented
as one lint pipeline rather than script-specific behavior.

**Rust home:** Extend `xtask lint` with package-set selection, quarantine
collection, and no-mangle checks; keep direct `cargo clippy` for the small
supported-core fast path only if needed for local ergonomics.

**Core-design outcome:** Lint policy is testable Rust logic with a single entry
point for contributors, pre-commit hooks, and CI.

**Suggested proof:**

```bash
cargo xtask lint --fast -- -- -D warnings
cargo xtask check-lint-policy
```

### P1 — Move golden reference generation into Rust-owned commands

**Current surface:** `golden-tests/generate_references.sh`,
`scripts/regenerate_golden_tests.sh`, and workflow-local Bash that clones
Tree-sitter grammars and invokes `tree-sitter`.

**Why it should move:** Golden tests are a core compatibility proof. The
workspace already has `xtask generate-golden`, `xtask diff-golden`, and
`xtask test-golden`; shell should not own grammar selection, reference paths,
or hash generation.

**Rust home:** Finish the `xtask::golden` command path so it owns reference
creation, hash writing, grammar lookup, and external command invocation. Leave
CI YAML as a thin dispatcher.

**Core-design outcome:** Tree-sitter parity proofs share the same Rust command
locally and in CI, reducing drift between developer and workflow behavior.

**Suggested proof:**

```bash
cargo xtask generate-golden python --force
cargo xtask diff-golden python --verbose
cargo xtask test-golden --verbose
```

### P2 — Consolidate WASM build scripts behind `xtask wasm`

**Current surface:** `runtime/build-wasm.sh`, `runtime/build-wasm-demo.sh`,
`wasm-demo/build.sh`, `scripts/check-wasm.sh`, and
`scripts/check-wasm-compat.sh`.

**Why it should move:** WASM support is an advertised projection surface, but
the build and compatibility checks are split across shell scripts and demo
folders. Rust should own target validation, wasm-pack dispatch, artifact
location, and compatibility diagnostics.

**Rust home:** Add `cargo xtask wasm build|demo|check|compat` and keep shell
wrappers only while external docs catch up.

**Core-design outcome:** WASM commands become discoverable through the same
repository automation surface as parser generation, policy, and proofs.

**Suggested proof:**

```bash
cargo xtask wasm check
cargo xtask wasm demo --dry-run
```

### P2 — Replace `scripts/process-utils.js` with a Rust helper or `xtask`
module

**Current surface:** `scripts/process-utils.js`.

**Why it should move:** This is durable process-management tooling in
JavaScript. If it is still used, it should be a Rust runner module shared by
`xtask`; if it is not used, it should be deleted instead of policy-registered
as general script debt.

**Rust home:** Either fold the behavior into the `xtask` runner used by
product-proof/release commands or remove it after confirming no call sites.

**Core-design outcome:** Process execution semantics become one Rust utility
instead of a separate Node dependency.

**Suggested proof:**

```bash
rg -n "process-utils|node .*process" scripts .github justfile xtask
cargo xtask product-proof --stable --dry-run
```

### P2 — Convert dashboard data generation and templates to Rust-owned outputs

**Current surface:** `dashboard-template/dashboard.js` and generated/static
web assets consumed by `cargo xtask init-dashboard`.

**Why it should move:** The dashboard can keep browser JavaScript for the UI,
but test-result summarization and data contracts should be Rust-generated and
schema checked. That boundary keeps UI presentation separate from repository
policy.

**Rust home:** Keep `xtask::dashboard` as the data/schema owner, emit a versioned
JSON schema, and make `dashboard-template` a presentation-only static asset.

**Core-design outcome:** Dashboard numbers derive from typed Rust results while
JavaScript remains a replaceable viewer.

**Suggested proof:**

```bash
cargo xtask dashboard-data --input target/corpus-results --output target/dashboard/data.json
cargo xtask init-dashboard --dir target/dashboard
```

### P3 — Shrink Tree-sitter C bridge to audited compatibility seams

**Current surface:** `tools/ts-bridge/ffi/shim.c`, `tools/ts-bridge/ffi/shim.h`,
`crates/ts-c-harness/tests/ts_c_shim.c`, and vendored Tree-sitter C files.

**Why it should move only selectively:** Some C is intentionally external
compatibility material. The migration target is not to rewrite vendored
Tree-sitter internals, but to minimize bespoke C shims and make Rust own the
ABI contract, table extraction model, and parity reporting.

**Rust home:** Keep `tools/ts-bridge` as an excluded compatibility crate, but
move shim contract tests, ABI hashing, and report generation into Rust tests or
`xtask` commands. Treat C files as fixtures or platform constraints with narrow
policy reasons.

**Core-design outcome:** The core parser/table design remains pure Rust while
Tree-sitter interop is a bounded adapter, not a second implementation path.

**Suggested proof:**

```bash
cargo build --manifest-path tools/ts-bridge/Cargo.toml
cargo test --manifest-path tools/ts-bridge/Cargo.toml
./scripts/smoke-link.sh ts-bridge
```

## Non-candidates

Do not spend migration effort on these unless their role changes:

- Benchmark and golden language fixtures such as JavaScript/Python inputs.
- Vendored Tree-sitter C sources and headers that are reference material.
- Generated documentation assets under `book/`.
- Platform-required YAML files for GitHub Actions, Codecov, Docker Compose, and
  pre-commit.
- Browser UI files that are purely static presentation and consume Rust-owned
  JSON contracts.

## Recommended sequence

1. Implement release/package migration first, because it unifies the publish
   surface with the package-boundary ledger.
2. Fold Python CI reporting into `xtask ci-plan`, because the Rust command
   already exists and the workflows can become thinner immediately.
3. Move product-proof and lint orchestration to typed `xtask` commands, using
   shell wrappers only as compatibility shims.
4. Finish the golden/WASM/dashboard migrations once the policy and release
   surfaces are stable.
5. Revisit the non-Rust allowlist after each migration and replace broad
   `scripts/**` allowances with narrower entries or retired audit records.
